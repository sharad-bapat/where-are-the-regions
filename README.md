# where-are-the-regions

Where are the regions? This tool reads a PDF and lists everything each page draws, in the order it's drawn: every line of text, every image, every drawn shape (lines, boxes, charts) and every annotation, each with a box saying where it sits on the page. It reads the file itself and never renders the page. It also marks things a reader can't see, such as white text, invisible text over a scan, or an image that's clipped away or off the edge of the page. A second step guesses what each image or drawing is (a photo, a scanned page of text, a table, a chart), and says how sure it is.

It's the fourth in a series, after [file-checker](https://github.com/sharad-bapat/file-checker) (what is this upload?), [scan-or-text](https://github.com/sharad-bapat/scan-or-text) (does this PDF need OCR?) and [wordbox](https://github.com/sharad-bapat/wordbox) (where is the text?). Deciding what to send to OCR is left to a later tool that reads this map.

The write-up, with a demo you can try, is at https://sharadbapat.com/experiments/where-are-the-regions/.

## Output

regions-cli prints one JSON object per file. Coordinates are PDF points from the top-left of the page as displayed (after the CropBox and /Rotate), so a box can be drawn straight onto a rendered page. Each page has:

- `map`: every region in drawing order, each with `what` (`text`, `image`, `vector` or `annot`), a box, `order` and `flags`. Text is mapped by line, vector paths by cluster of touching paths.
- `words`: every word with its box and baseline, grouped by wordbox's rules, plus `ink` when the glyphs' outlines reach past that box (italic overhang, capitals taller than the font's /Ascent).
- `images`, `paths` and `annots`: the parts the map's regions are built from, each with its own box and flags.
- `regions`: images scored as OCR candidates by `regions/src/ocr.rs`, kept here until the OCR tool exists.

```json
{"id":2,"what":"text","x0":48.2,"y0":253.9,"x1":292,"y1":263.2,"order":2,"words":[0,10],"t":"have forensic utility (Parsons and Coble 2001; Lee et al.","flags":[]}
{"id":44,"what":"image","x0":48.2,"y0":51,"x1":292,"y1":183.5,"order":1896,"image":0,"obj":4,"flags":["mask","clipped"]}
```

Some flags say why a mark may not show: `hidden` (cut away entirely by its clip), `clipped` (cut in part), `offpage` (none of it on the page), `white` (painted only in white), `invisible` (text in render mode 3 or 7), `empty` (a path that paints nothing) and `no_appearance` (an annotation with nothing to draw). The others describe the mark: `fill`, `stroke`, `shading`, `mask`, `inline`, `strips` (one picture drawn as several images), `rotated`, `annot` (drawn by an annotation's appearance) and `undecodable` (text the file gives no Unicode for).

The kind layer is in the library's `kind` and `vkind` modules. The browser build's `kinds_json` gives it for each image and vector cluster, and `thumbs --kinds` and `vkinds` print it with the reasons.

## Layout

- `regions/`: the library, the CLI (`regions-cli`), and `thumbs` and `vkinds` for the kind layer. `src/tables.rs` is generated by `tools/gen_tables.py`.
- `wasm/`: the browser build, `extract_json(bytes)` and `kinds_json(bytes)`. It's a separate crate so the frozen library stays untouched. `tools/wasm_check.mjs` confirms its output equals the native output byte for byte on all 1,553 test files.
- `demo/`: the browser demo. pdf.js 6.3.289 (Apache-2.0, bundled with its licence) draws the page, and the map's regions are boxed on top, one colour per layer, with the kinds and flags listed beside it. `tools/samples.py` makes its four made-up sample PDFs, and `tools/demo_check.mjs` drives it in headless Chrome.
- `tools/`: the test sets, the ink test (`ink_check.py`), the scorers, the freeze check, the reader comparison (`ink_baseline.py`) and the timing scripts.
- `data/real/`: the labels for the real pages.
- `results/`: every number below, with how it was measured. `results/README.md` lists the files.

## Data

The exact layer has two checks that don't depend on the parser. The ink test renders each page with PyMuPDF 1.24.9 at 150 dpi and asks what share of the dark pixels falls inside the map's boxes (grown by 1 pt), and which regions hold no ink at all. The marks set (`tools/build_marks.py`) is 200 one-page PDFs whose every mark has a box known by construction. Two more constructed sets cover the image kinds (`tools/build_set.py`, 600 pages) and the vector kinds (`tools/build_vectors.py`, 240 pages). Each set has a tune and a held-out split.

Real pages come from [govdocs1](https://digitalcorpora.org/corpora/file-corpora/files/): thread 003 for tuning (278 files, 967 labelled pages) and thread 004 held out (235 files, 704 labelled pages). The image labels come from Tesseract run on each image's own pixels, and Claude checked a sample of them by eye. The 150 vector clusters per thread were labelled by eye from contact sheets by Claude, without the predictions in view. govdocs1 is public domain and isn't redistributed; `data/real/` holds only the labels.

The rules were tuned on the tune data only, then frozen by hash (`results/frozen.sha256`, checked by `tools/check_frozen.py`, which every held-out tool calls) and run once on the held-out data against targets set beforehand. Fixes found after a held-out run went in their own commits, each relocked, and they're reported apart from the held-out numbers.

The ink test has one bias worth knowing. The judge is MuPDF's renderer, so a mark MuPDF draws differently from other renderers counts against the map (results/findings.md has two such cases).

## Results

All runs on a Windows laptop, 27 September to 2 October 2026.

The exact layer, held out, with the rules frozen (results/exact-heldout.md):

| Set | Target | Result |
|---|---|---|
| Marks set, 95 pages, 1,015 marks | 99.5% within 1 pt, no extra regions | 1,015 of 1,015, no extras |
| Constructed set, 300 pages | every page at 99.9% of ink | all 300 at 99.99% or more |
| govdocs1 004, 704 pages | every page at 99.5% of ink | 703 of 704 (one page at 99.26%) |

The fixes made since were for a substituted Symbol font, Type 3 glyph boxes, and glyph outlines from every kind of font program. With them, 703 of the 704 held-out pages are at 100% of ink and the last one misses 3 pixels. All 967 labelled pages of 003 are at 100%.

The same ink test on maps built from other readers' boxes, govdocs1 003 (results/ink-baseline-readers.md):

| Reader | Pages at 100% | Worst page | Missed ink |
|---|---|---|---|
| regions-cli | 967 of 967 | 100% | 0 pixels |
| PyMuPDF get_bboxlog | 966 | 56.42% | 710,374 pixels |
| pdfplumber 0.11.9 | 722 | 36.55% | 781,588 pixels |
| PyMuPDF get_text, get_image_info, get_drawings | 720 | 14.88% | 2,076,528 pixels |

bboxlog is MuPDF reporting on MuPDF's own render, so it has the advantage on this test. It loses one page, where the background is filled with a tiling pattern and bboxlog boxes it by the tile.

The image kinds met their held-out targets (results/kind-heldout.md). On the constructed set, 147 of 150 text images were found and none of the 88 other images was called text. On real and constructed images together, 91.4% of the kinds given at confidence 0.9 or more were right. The vector kinds didn't (results/vkind-heldout.md): the constructed set was right 117 of 117, but on real held-out pages only 66.7% of the kinds given at 0.9 or more were right, against a target of 90%. On 003, where the rules were tuned, the same figure was 90.2%, so they fit those files and didn't carry over. I'd treat the vector kinds as experimental.

Speed, median a page (results/speed.md): 2.03 ms on 003 and 1.69 ms on 004 natively, and 1.90 and 2.55 ms in WebAssembly under Node. A few files set the totals: one 76-page file in 004 takes about 1.3 s a page. The WebAssembly build is 814 KB, 330 KB gzipped, since it decodes inline images' pixels too (772 KB before).

## Findings about other software

The checks turned up some behaviour in other tools, each with its evidence in results/findings.md. None is reported upstream yet.

- PyMuPDF boxes a path filled with a tiling pattern by its tile at the pattern origin, not by the area it paints.
- PyMuPDF's `get_text("words")` leaves out glyphs whose codes decode to control characters.
- pdfminer.six ignores the `sh` operator, so pdfplumber lists no shadings.
- ttf-parser fails on any CFF glyph that uses the deprecated `dotsection` operator, which Adobe's Type 2 spec says to treat as a no-op. About 2% of the charstrings in govdocs1's embedded CFF fonts use it.
- MuPDF doesn't draw a round-capped stroked point given as `m h`, and pdfium draws zero-length lines with butt or square caps, which the spec says produce nothing.
- reportlab and pdfminer.six each carry standard-font metrics that differ from Adobe's core-14 AFM files.

## Limits

The vector kinds are experimental (above). Only PDFs are read, not image files. There's no reading order and no grouping beyond word, line and touching paths. For fonts that aren't embedded, glyph boxes use Adobe's metrics, while MuPDF draws them with URW's Nimbus fonts, which differ by a few units on some glyphs. JPX and JBIG2 images aren't decoded, so they get no image kind. The slowest files haven't been profiled.

## Commands

```
cargo build --release --manifest-path regions/Cargo.toml
regions/target/release/regions-cli file.pdf
cargo test --release --manifest-path regions/Cargo.toml
(cd wasm && wasm-pack build --release --target web)   # then copy pkg/regions_wasm.js and pkg/regions_wasm_bg.wasm into demo/
python tools/samples.py demo/samples
node tools/demo_check.mjs <demo url> <screenshot dir>
python tools/check_frozen.py
python tools/ink_check.py real data/real/tune-003.jsonl <govdocs1>/003 --out=ink-003.jsonl
python tools/score_map.py tune
python tools/score_vkinds.py
node tools/wasm_check.mjs <folder of PDFs>...
python tools/speed.py <govdocs1>/003 <govdocs1>/004
```
